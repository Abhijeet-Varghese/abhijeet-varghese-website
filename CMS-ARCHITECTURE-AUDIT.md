# Whole-Website CMS Architecture Audit + Migration Plan
### Abhijeet Varghese — AV OS publishing system
**Date:** 2026-09-08 · **Scope:** read-only architectural discovery (no changes made) · **Reference impl:** the Recruiters template

> Evidence base: direct reads of `avos-php/backend/publish/PublishEngine.php` (3,187 lines), the live MariaDB `content_store`, `backend/controllers/ApiController.php`, the admin SPA (`public_html/admin/app/`), the publish scripts, and the `site-template/` asset tree. Line numbers cited where relevant.

---

## 01. Executive Summary

AV OS is a **flat-file static-site generator driven by a JSON document store**, wrapped in a PHP admin + API. There is no page served dynamically from the DB on the public site: `PublishEngine` reads the entire content document (`content_store`, 11 top-level keys), renders every page to static HTML, validates the build, and atomically swaps it into `public_html/site/`.

The renderer is a **single large class** with three tiers of rendering:
1. **Section-driven** home page (`renderHomepage`, 9 section types).
2. **Dedicated page renderers** keyed on a page record's `template` field — `About`, `Experience`, `Portfolio`, `Contact`, `Blog Index`, and now `Recruiters`.
3. **Generic block renderer** (the fallback) — 14 block types — used by `Page`-template records.

Projects (case studies) have their own dispatch with one bespoke static template (Orange Business) and a generic case-study fallback.

**The system already contains the correct architectural pattern** for bespoke creative pages — a static canonical template in `backend/publish/templates/` with placeholders, rendered by a dedicated method, sharing chrome/footer/SEO/analytics. The Orange Business case study and the new Recruiters page both use it. The architectural debt is that **most of the site's bespoke, art-directed pages (Home, About/Story, Experience, Portfolio) are generated by hard-coded PHP heredocs inside `PublishEngine.php`**, while the `abhijeetvarghese/*.html` hand-built files are **not consumed by the publisher at all** (only their `css/js/assets` are synced) — a three-way split between *frontend hand-built HTML*, *hard-coded PHP renderers*, and *published HTML* that has already begun to drift.

The target state: **content lives in the CMS document; presentation for exceptional pages lives in versioned canonical templates** (the Recruiters pattern); generic pages keep using blocks. The CMS can then regenerate any page without destroying creative work.

## 02. Current Architecture

**Request / runtime**
- Public site: PHP built-in server (`php -S 0.0.0.0:8092 router.php`) in dev; Apache + `.htaccess` on Hostinger in prod. `router.php` maps `/` and page URLs into `public_html/site/`, serves `/api/*` via `public_html/api/index.php`, `/admin/*` via `public_html/admin/`, and `/media/*` via `media.php`.
- Admin: a **single-page app** (`public_html/admin/app/index.html` + JS modules) talking to a JSON API (`ApiController`, 2,904 lines). Auth is session + TOTP 2FA.
- Data: MariaDB. Most site content is one JSON blob per collection in table `content_store` (key/value `key_name` → `data` JSON). Operational/feature tables exist separately (leads, media, SEO, AI, analytics, etc.).

**Publishing pipeline (the core)**
```
content_store (JSON)  ──┐
site-template/ (css,js,assets) ─┤
storage/uploads/ (media) ─┤
                         ▼
              PublishEngine::publish()
                         │  build into staging dir (buildSite)
                         │  validateBuild() + internalLinkCheck()
                         ▼
              atomic rename staging → public_html/site
                         │  verifyPublishedSite() (auto-rollback on failure)
                         │  DeploymentModel snapshot + audit
                         ▼
              mirrorSite() (dev mirror, optional)
```
- Publishing is **atomic with automatic rollback** (`PublishEngine.php:2742`): builds to a staging dir, validates, swaps, health-checks, and reverts on failure. This is a strong foundation.
- Triggers: auto-publish after CMS save (debounced via `publish_queue` + `PublishQueue::drainAndPublish`), the 60-second `auto-publish.php` cron, manual "Publish" in admin, and CLI.

## 04. CMS Content Model

All editorial content lives in `content_store` (table: `content_store(key_name PK, data LONGTEXT JSON, …)`). 11 keys:

| key | shape | size | purpose |
|---|---|---|---|
| `settings` | object | 1.4 KB | siteName, tagline, email, phone, theme, designTokens, favicon, logo, ogImage, metaDescription, keywords, socials[], availability |
| `nav` | `{primary[], footerColumns[], copyright}` | 2.0 KB | navigation labels/hrefs/page mapping |
| `sections` | array (9) | 7.2 KB | **homepage** sections: hero, clients, capabilities, work, thinking, journey, ai, focus, contact |
| `pages` | array (12) | 28 KB | all CMS pages (see §05) |
| `projects` | array (6) | 6.2 KB | case-study projects (3 published, 1 scheduled, 2 draft) |
| `articles` | array (8) | 6.6 KB | essays (4 published) + journal (2 published, 2 draft/review) |
| `media` | array (13) | 2.5 KB | media library references |
| `clients` | array | 1.6 KB | logo wall |
| `testimonials`, `downloads`, `seo` | arrays/obj | <2 KB | supporting content |

**Page record schema (actual fields observed):**
`id, title, slug, status (published|draft|scheduled|review), template, seo{title,desc,…}, updated, blocks[]`.
- `blocks[]` items: `{type, content{…}}`. Used only by the generic renderer and by `About`/`Experience` (which consume blocks but render their own bespoke layout).
- **Special fields on projects:** `id (prj-n), client, industry, year, role, summary, challenge, approach, outcome, image, imageAlt, gallery[], slug, caseStudyPath, caseStudyTemplate, comingSoon, legacyPaths[], preserveFrame, status`.
- Recruiters page still carries its legacy 3 blocks (`hero, prose, card`) but they are **ignored** because `template: Recruiters` routes to the static template. (Harmless; could be cleaned.)

**No page-level JSON/rich-text beyond blocks + a free-form `content`.** There is no schema for per-page CSS/JS assets, body class, or template selection — template is a free-text string.

## 06. PublishEngine Dispatch Map

`renderPage(array $page, …)` (`PublishEngine.php:1372`):
```
template === 'Recruiters'  → renderRecruiters()      → templates/for-recruiters.html   [TPL]
template === 'About'       → renderAbout()           [DED-PHP, consumes blocks]
template === 'Experience'  → renderExperience()      [DED-PHP, consumes blocks]
template === 'Portfolio'   → renderPortfolio()       [DED-PHP, uses projects]
template === 'Contact'     → blocks (blockContact)   [BLOCK w/ booking]
template === 'Blog Index'  → blog index renderer     [DED-PHP, uses articles]
template === 'Page' / other→ foreach blocks → match:  [BLOCK]
   hero|prose|image|quote|timeline|list|capabilities|logowall|cta|card|cases|articles|contact|sitemap
   default → "<!-- unknown block: {type} -->"
```
Then every page is wrapped by **`shell()`** which assembles: `head()` → skip-link/progress → `chrome()` (header/nav/mobile menu + a `page-close` back control) → `<main>{body}</main>` → `footer()` → `<script src="js/main.js">`.

`buildSite()` (`:2541`) writes, in order: `index.html` (home), all `pages`, all `articles`, all `projects` (case studies + legacy redirects), `sitemap.xml`, `robots.txt`, `404.html`, optional search, design tokens, analytics, `syncMedia()`, `.htaccess`.

**Unknown-template / unknown-block behavior (verified):**
- Unknown `template` → falls through to generic block render (no error).
- Unknown `block.type` → emits an HTML comment `<!-- unknown block: x -->` (silently drops content).
- Case study: `comingSoon` → placeholder; `caseStudyTemplate==='orange-business-ebc'` or `id==='prj-1'` → Orange template; **all other projects → the single generic case layout**, regardless of creative needs.

## 09. Asset Pipeline

```
frontend (abhijeetvarghese/css|js|assets)
        │  sync-frontend.php  (sha256 manifest, idempotent, only css/js/assets/fonts)
        ▼
site-template/css|js|assets  (canonical asset store)
storage/uploads/media/*      (CMS-uploaded media referenced as media/…)
        │  syncMedia() during buildSite:
        │    • copyDir site-template/{css,js} → out/{css,js}
        │    • copyDir site-template/assets   → out/assets
        │    • walk content for "media/…" strings → copy storage/uploads → out/assets
        ▼
public_html/site/{css,js,assets}
```
- **Cache busting:** `assetVersion()` hashes every file under `site-template/css` and `…/js` (path + sha256), producing `?v={AV_VERSION}-{12-hex}`. Deterministic and content-aware. Output: `2.4.20-714ca85b1f7c`.
- **Image sizing:** `imageSizeAttrs()` reads intrinsic dimensions from the template to set width/height (CLS protection) for renderer images. Static templates set their own.
- **Fonts:** self-hosted woff2 in `assets/fonts/`; LCP font preloaded in `head()` for home/articles.
- **Gaps/inconsistencies:**
  - Page-scoped CSS/JS for DED-PHP pages (Portfolio/Orange/Recruiters) only load because the files exist in `site-template` and are blanket-copied; there is **no per-page asset declaration** — every page's `<head>` (via `shell/head`) only auto-includes `styles.css`. Page-scoped `<link>`/`<script>` are hand-added inside the static templates / hard-coded renderers. The generic `head()` has no mechanism to register a page-specific stylesheet.
  - Media is discovered by **string-walking** for the `media/` prefix; a media path not matching that prefix (e.g. an absolute or differently-prefixed reference in a bespoke template) won't be copied. Bespoke templates reference assets already in `site-template/assets`, so this works, but it is implicit.

## 10. Shared Chrome

- **`chrome($s,$nav,$active,$prefix='')`** builds: brand logo (from settings), primary nav (from `nav.primary`; marks `aria-current` on the active page), the "Start a conversation" button, the mobile hamburger + mobile menu dialog, and the floating `page-close` back control.
- **`footer($s,$nav,$prefix='')`** builds brand block, footer columns (`nav.footerColumns`), social icons (`SOCIAL_ICONS` map), back-to-top.
- **Prefix handling:** `prefixedHref()` rewrites document-relative links with a prefix (`../../` for the nested Orange page; `''` for top-level). It leaves absolute `/`, `//`, `#`, and protocol URLs untouched.
- **Global scripts/styles:** `head()` always loads `css/styles.css?v=…`; `shell()` always appends `js/main.js?v=…`. The `js` class + `reveal-failsafe` timer is injected in `head()`.
- **Page-scoped assets/styles:** the Recruiters and Orange templates add their own `<link>`/`<script>` and body class (`rp`). The DED-PHP pages pass a `$bodyClass` to `shell()` (e.g. `home-arena`, `about-page`, `portfolio-page`) and rely on `styles.css` scoping.
- **Path-assumption risk:** the nested Orange template hard-codes `../../` relative links in its template *and* receives `../../` chrome. Any new bespoke template placed at a different depth must get the matching prefix and relative asset paths. Top-level templates (Recruiters) are simplest and safest.

## 11. SEO + JSON-LD

Generated centrally in `head()` for every shell page:
- `<title>`, meta description, keywords, robots (`index,follow,max-image-preview:large`), theme-color, canonical (`{SITE_URL}/{file}`), favicon, font preload.
- Open Graph (`og:type/url/site_name/title/description/image`) + Twitter card.
- Default JSON-LD from `shell()`: a generic `WebPage` node (name/url/inLanguage).

**Page-specific JSON-LD (override the default per renderer):**
- Home → `Person` (jobTitle Creative Systems Leader, email, telephone, image, sameAs).
- Portfolio → `CollectionPage` with `hasPart: CreativeWork[]`.
- Orange EBC → full `@graph`: Person, CreativeWork, Article, WebPage, BreadcrumbList, ImageObject, VideoObject[] (videos conditionally included if files exist).
- Recruiters → `ProfilePage` + `Person` with `knowsAbout[]` and `memberOf: AVGC-XR Rajasthan`.
- Articles → `Article`.

**Flags / duplication risks:**
- The hand-built `abhijeetvarghese/story.html` contains its own `AboutPage` JSON-LD, but the **published** About (from `renderAbout`) goes through `shell()` which emits the generic `WebPage`. → JSON-LD differs between the dev file and the live site (drift). Same class of risk for any hand-built `<head>`.
- Canonical URLs are derived from the output filename (`AV_SITE_URL + /file`), correct for top-level pages; the nested Orange template hard-codes its own canonical.
- Static templates own their full `<head>` (Recruiters/Orange), so their SEO is not run through `head()` — they must (and do) replicate meta/OG/canonical manually. This is flexible but means SEO improvements to `head()` don't propagate to static templates automatically.

## 12. Analytics

- **First-party (AV OS):** `injectAnalytics()` (`:2978`) appends a fixed `<script>` before `</body>` in **every** built HTML file, **skipping any file that already contains the string `api/analytics/track`** (dedup guard, `:3109`). This is why Recruiters can ship `{{ANALYTICS}}` empty and Orange ships no inline analytics — both get exactly one copy injected.
- **External (GA4/GTM/Clarity):** `injectExternalAnalytics()` (`:2929`) injects configured third-party snippets into HTML files from the integration hub settings.
- **Nested pages:** the injected snippet uses absolute `/api/analytics/track`, so it works at any directory depth.
- **Duplication risk:** low, because of the string dedup guard — but it is a *content-string* guard. If a static template ever includes the literal `api/analytics/track` (the original hand-built recruiter page did) it will be skipped and rely on its own copy; today both templates correctly avoid double-inclusion. Recommendation: keep static templates free of inline analytics and rely on injection (as Recruiters now does).

## 13. Preview System (critical finding)

- **There is no on-the-fly render/preview endpoint.** Grep for any controller method that invokes `PublishEngine` to return HTML for a draft returned **nothing**. `PublishEngine` is only ever invoked to **publish to disk** (save/publish/preflight-dry-run).
- Admin "preview" surfaces are:
  - **Section/block previews** (`views-build.js` `previewSection`, article `data-preview`): these render a **mock HTML fragment inside a modal from the SPA's local state** — they do **not** call the publisher and do **not** reflect the real renderer output.
  - **Live-site viewing:** the admin links to the generated `public_html/site/` (the last published build). Drafts saved with `publish:false` are **not visible** anywhere as rendered HTML until published.
- **Consequence:** preview ≠ publish source for the modal previews (mock vs real renderer). The *actual* rendered truth only exists after a publish. This is architecturally unsafe for creative iteration: a page can look correct in the editor mock but publish differently (this is exactly the class of bug the Recruiters work avoided by making publish deterministic and testable).
- **Mitigation already present:** `preflight()` (dry-run build + validate, no disk swap) and the atomic rollback give a safety net, but no visual draft preview of the true renderer.
- **Verdict:** preview and production share the same *content* (the doc) but **not** the same *rendering path* for editor previews. Static-template pages (Recruiters/Orange) have **no editor preview at all** beyond the live published file.

## 14. Admin / CMS Editing

- Pages/sections/projects/articles are edited in the SPA; state is persisted via `PUT /api/content` (whole document) with optional `publish:false` draft mode, then auto-published through the queue when `auto_publish` flag is on.
- **Template selection:** the page editor does **not** expose a validated template dropdown tied to renderers. Sections offer a fixed list (`Hero, Clients, Capabilities, Featured Work, Thinking, Journey, AI, CTA, Contact, Footer, Custom`); pages default new records to `template: "Page"` (`views-live.js:376`). The `data.js` page directory is **hard-coded mock metadata** and still lists For Recruiters as `template: "Page"` (stale vs DB which is `Recruiters`).
- **Unknown template values are accepted** (free text, no allow-list) — an unrecognized value silently falls back to generic blocks.
- **Static-template pages (Recruiters/Orange):** the CMS cannot edit their copy/structure — content lives in the template file/PHP. They are managed in code, not in the admin. This is the intentional content/presentation split but means a non-developer cannot edit recruiter copy.
- **Publishing does not mutate content**, but it **does overwrite `public_html/site/`** wholesale each build (that is the mechanism that previously destroyed the hand-placed recruiter file). Source-of-truth safety depends entirely on a page being produced by a renderer/template — which is now true for Recruiters.
- **Minimum changes to make first-class templates CMS-manageable:** (a) a renderer/template registry + allow-list in the API and the page-editor dropdown; (b) an optional `templateData`/content bag passed into static templates (so copy is editable while markup stays in code); (c) a real "preview this page through PublishEngine" endpoint; (d) refresh stale `data.js` mock metadata.

## 17. Content vs Presentation Analysis

**Where the split already works:**
- Projects/case studies keep **content** (title, client, role, challenge, approach, outcome, media) in the CMS document, separate from presentation.
- Articles keep **content** (title, body, excerpt, cover, readTime) in the CMS; `renderArticle()` owns presentation.
- Settings/nav/clients/media are pure content consumed by shared chrome.
- Recruiters/Orange keep **presentation** (markup, typography, animation, interaction) in a code template while chrome/SEO/analytics are shared.

**Where it does not:**
- **Home/Story/Experience/Portfolio copy is hard-coded in PHP heredocs** inside `PublishEngine.php`. Presentation *and* content are fused into engine code; editing copy requires editing the engine. Blocks partially de-duplicate this for About/Experience (content in blocks) but the layout strings are still hard-coded.
- **Static templates (Recruiters/Orange) fuse content into the template file** — presentation is clean, but editorial copy is not CMS-editable. Ideal end-state: templates receive a `templateData` content bag from the page/project record.
- **Two parallel HTML sources** (`abhijeetvarghese/*.html` vs engine output) with no enforcement that they agree — already drifting.

**Target principle:** *Content (copy, media references, structure, metadata) lives in the CMS document. Presentation (layout, typography, motion, interaction, composition) lives in versioned renderer/template code. The publisher deterministically combines them.*

## 20. Current Architectural Problems

1. **HTML has three competing sources of truth** — hand-built `abhijeetvarghese/*.html` (unused by publish), hard-coded `PublishEngine.php` heredocs (actual source for most pages), and canonical `templates/` (only 2 pages). Already drifting (home byte sizes differ).
2. **Bespoke pages are encoded in engine code** — Home/Story/Experience/Portfolio presentation + copy live in a 3,187-line PHP class, making creative iteration an engine edit and review harder.
3. **No real preview** — editor previews are mock fragments; the true renderer only runs on publish. Preview/publish divergence.
4. **Template field is free-text with no registry/allow-list** — unknown templates silently fall back to generic blocks (the exact mechanism that overwrote Recruiters).
5. **No per-page asset declaration** — page-scoped CSS/JS depend on files existing + blanket copy; `head()` can't register them generically.
6. **Static-template copy is not CMS-editable** and there is no content-bag contract for templates.
7. **SEO/JSON-LD diverges** between hand-built files and published output; static templates re-implement `<head>` manually.
8. **Stale admin mock metadata** (`data.js` still says Recruiters = Page).
9. **Media discovery is string-pattern based** (`media/` prefix) — implicit, fragile for bespoke templates.
10. **Recruiters' legacy blocks** remain in the record (ignored) — harmless but misleading.

## 22. Target Architecture

```
                        CMS content_store (single source of truth)
                        settings · nav · sections · pages · projects
                        articles · media · clients · practice(ai) · memberships
                                          │
                    ┌─────────────────────┼──────────────────────┐
                    ▼                     ▼                      ▼
            GENERIC PAGES          STRUCTURED PAGES         BESPOKE PAGES
            (Page template)       (articles, indexes,      (Home, Story, Experience,
            blocks renderer       contact, BPCL/Army)      Portfolio, Recruiters, Orange)
            utility/prose         structured renderers     dedicated renderer
                                                           → canonical static TEMPLATE
                    │                     │                      │
                    └─────────────────────┼──────────────────────┘
                                          ▼
                     shared shell: head() · chrome() · footer()
                     shared SEO/JSON-LD builder · analytics injection
                                          ▼
                     asset pipeline (site-template css/js/assets,
                     content-hash versioning, per-page asset manifest)
                                          ▓
                     PublishEngine build → validate → atomic swap → verify
                                          ▓
                              public_html/site (static)
```
Principles:
- **Two coexisting tracks**, intentionally not unified: generic blocks for utility content; canonical templates for exceptional creative pages.
- A **template registry** maps `template` → renderer/template/required-assets/body-class; unknown values fail loudly (build warning/error), never silently downgrade.
- Templates receive a **`templateData` bag** from the page/project record so copy is editable while markup/code stays version-controlled.
- **One shared head/SEO/JSON-LD/analytics** path, reused by templates via placeholders (extend the Orange/Recruiters placeholder set).
- **Preview runs the real renderer** on a draft document.

## 23. Recommended Migration Order

Prioritized by risk reduction and dependency order (not "migrate everything"):

0. **Freeze & back up** — Recruiters/Orange are the reference; no engine changes without snapshot/rollback. (Deployments already snapshot.)
1. **Template registry + allow-list** (engine + API + admin dropdown). Lowest risk, highest safety: prevents silent fallback. Add a build-time warning/error for unknown templates. *(Shared infrastructure)*
2. **Real preview endpoint** (render a draft page through PublishEngine to an authenticated temp response). De-risks every later migration. *(Shared infrastructure)*
3. **Per-page asset manifest + shared head partial for templates** (declare css/js/bodyClass; centralize SEO/OG/JSON-LD/analytics placeholders). *(Shared infrastructure)*
4. **Home → canonical template.** Highest visibility; currently the most heredoc-heavy. Move markup to `templates/home.html`; move copy into `sections` (already CMS data) consumed by the template.
5. **Story/About → template.** Content already largely in blocks; lift the bespoke layout into a template, keep blocks as the content bag.
6. **Experience → template.** Structured six-role timeline; content in blocks/project-like records.
7. **Portfolio → template.** Project-driven; reuse project content.
8. **Case studies (BPCL/Indian Army)** — decide: keep generic structured renderer (acceptable) or build one richer shared case template that reads project content. Lower urgency (content is already separated).
9. **Contact / blog indexes / articles** — structured; minor template hygiene only.
10. **Content collections:** lift AI practice nodes + AVGC membership into site-level content (single truthful sources).
11. **Final CMS cleanup:** remove legacy recruiter blocks; refresh admin `data.js`; quarantine/delete unused `abhijeetvarghese/*.html` (keep css/js/assets); document source-of-truth.
12. **Regression gate** (see §24) wired into publish for every page.

Each step ships behind the atomic publish + rollback, and is independently revertible.

## 24. Test / QA Strategy (reusable per migrated page)

The Recruiters publish-twice/three-times behavior is the benchmark. Per page, automate:

1. **Publish #1** → build, validate, swap.
2. Assert: HTML generated; CSS/JS/images/fonts return 200; no failed requests; canonical/OG/JSON-LD present; analytics exactly once.
3. **Publish #2** → compare output **byte-identical** (normalize only for expected timestamps).
4. **Publish #3** → compare again (idempotency under repeated CMS saves).
5. **Playwright (Chromium) desktop + mobile:** zero JS errors; zero failed requests; **no horizontal overflow** at 1440px and 390px; interactions work (accordions, tabs, diagrams, cursor where present); keyboard operable (Tab/focus/Enter, `aria-expanded` correct).
6. **Reduced motion** emulation: intro/animations disabled, all content visible/focusable.
7. **axe-core:** 0 violations (contrast, ARIA roles, heading order, landmarks).
8. **Content preservation:** expected copy/data present (assert key strings: titles, the six career roles, the three case clients, AVGC phrase, AI nodes); truth checks — no AI labels on prj-1/2/3; AVGC wording exact.
9. **SEO:** title/description/canonical unique per page; exactly one expected JSON-LD type; no duplicate schema.
10. **Preview parity:** the draft-preview render matches the published render for the same content.
11. Gate as a `preflight`/CI step so a regression blocks the atomic swap (rollback path already exists).

## 28. Final Recommendation

The codebase already contains the right answer — it just uses it on only two pages. **Standardize the Recruiters/Orange pattern as the supported way to build bespoke pages**: a CMS page record with a registered `template`, a dedicated renderer, a canonical static template under version control, shared chrome/SEO/analytics, and a deterministic hashed asset pipeline. Keep generic blocks for utility pages. Add the three missing safety rails — a **template registry**, a **real preview that runs the same renderer as publish**, and a **per-page asset/head manifest** — before migrating Home/Story/Experience/Portfolio out of the engine heredocs. Move editorial copy into the CMS and leave presentation in code. Gate every migration on the **publish-three-times byte-identity + Playwright/axe/overflow** acceptance test that Recruiters already passes.

Done this way, the CMS can regenerate a genuinely world-class, highly bespoke creative site on every publish without ever destroying the creative work — and the editor, the preview, and the live site all tell the same truth.
